01 / Self-hosted human verification

Prove they are human without telling anyone else

Five interactive challenges, a proof of work on every attempt, and behavioural scoring that grades how an answer was produced rather than only what it was. One Go binary, no external dependencies, no cookies and no fingerprinting — on your own hardware.

02 / What your visitors see

Every challenge, running right here

These are not screenshots. Each panel below is the component the service ships, mounted against artwork a real deployment generated, so what you drag on this page is what a visitor drags on yours. Switch the language in the panel to see the Persian side.

Slider jigsaw

A piece is cut out of a generated background and has to be slid back into the notch it came from. The board and the piece are two images; the geometry that connects them never leaves the server.

Graded on
Final offset, within 6 px at the default difficulty.
Keyboard
Arrow keys move the handle, and score the same as a drag.
Artwork
Six geometric styles over eight palettes named for Persian pigments — lajevard, zaferan, anaar.

Rotate

A disc is handed over at a random angle and has to be turned upright. There is no text to read and nothing to recognise — which is why it travels well across languages.

Graded on
Whether the correction cancels the offset, within 10°.
Keyboard
Arrow keys turn the disc in 2° steps.
Artwork
A girih emblem drawn from the session seed, so no two discs repeat.

Click in order

Shapes are scattered over a background and three of them have to be selected in a stated order. Ordering is what makes it awkward to automate: recognising a star is easy, knowing it is the second one wanted is the part that costs.

Graded on
Each click landing within 1.3 icon radii, in sequence.
Keyboard
A crosshair moves with the arrow keys; Enter selects.
Prompt
Shape names are translated, never drawn into the image.

Drag and drop

Three shapes sit in a tray under outlines cut into the board. Each one has to be carried to the outline that matches it — the most physical of the four, and the one that produces the richest motion to grade.

Graded on
Every piece centred within 0.8 of the slot radius.
Keyboard
Tab picks a shape up, arrows move it, Enter drops it.
Difficulty
Adds pieces and tightens the tolerance rather than blurring the image.

Accessible question

Sliders and drag targets are unusable with a screen reader, so every puzzle carries a link to this: a short localised question, answerable from the keyboard alone. It is offered, never imposed — no site key can force it, and asking for it is never rationed.

Graded on
The chosen answer, and the proof of work that came with it.
Not graded on
Motion. Holding this to a pointer threshold would break it for the people who need it.
Content
Arithmetic and category questions, generated per session from the locale's own word list.

Preview This page has no service behind it, so it grades in your browser and the answers are in the bundle. A deployment works the other way round: the puzzle is generated server-side, the artwork is redrawn from a seed the browser never sees, and the answer is graded by /v1/solve — which is also where the proof of work and the motion trace are checked.

03 / The round trip

What happens between the click and the token

Most visitors never see a puzzle. The interactive challenge is the expensive path, kept for the sessions that have earned it.

01

The widget loads

One script on your page creates an iframe pointing at the captcha service. The challenge runs on the service's origin, so the host page cannot read the artwork, inspect the DOM or synthesise the events that solve it.

02

The browser pays first

Opening a session hands back a proof of work. A few tens of milliseconds for one visitor; a real bill for anyone solving captchas in bulk, and it escalates with every failed attempt.

03

Signals are scored

A narrow set of environment signals is weighed — no canvas or WebGL fingerprinting, no font probing, nothing that could identify the same person on another site.

04

A puzzle, or not

A clean session passes without seeing anything. A suspicious one gets a challenge, and a fraction of the clean ones do too — because a defence that never fires is one an attacker can plan around.

05

The answer is graded twice

Once on geometry, once on the motion that produced it. A script that computes the right slider offset and delivers it in a straight line at even intervals is refused.

06

Your backend decides

A pass mints a single-use token. Your server exchanges it at /v1/siteverify for a verdict and a score, and refuses the request unless it comes back successful.

04 / Properties

Deliberate choices, not defaults

Nothing to track with

No cookies, no cross-site identifier, no fingerprinting. Addresses are hashed with a per-process secret and everything expires within minutes.

A genuine accessible path

A keyboard-operable, localised question sits behind a link on every challenge — translated, not a CAPTCHA audio file nobody can parse.

Persian as a first language

Not a translation bolted on. The layout mirrors, the numerals are Persian where a Persian reader expects them, and the artwork comes from girih and tilework rather than clip art.

Sessions cost a kilobyte

Artwork is never stored. The seed and the geometry are, and any image is redrawn deterministically when the browser asks for it.

One binary, or one container

Everything is embedded: the widget, the fonts, the locale bundles, the renderer. In-memory storage for a single instance, Redis for more — spoken directly, with no client library.

A familiar shape

The widget API and the verification endpoint mirror reCAPTCHA and hCaptcha closely enough that an existing integration usually needs only its script tag and site key changed.

05 / Integrate

Two steps, and one of them is a script tag

The widget adds a hidden pcaptcha-response field to the surrounding form. Your server exchanges it for a verdict. Never trust the browser's word that the captcha was solved.

On the page html 
<form method="post" action="/signup">
  <input name="email" type="email" required>

  <div class="pcaptcha" data-sitekey="YOUR_SITE_KEY"></div>

  <button type="submit">Sign up</button>
</form>

<script src="https://captcha.example.com/v1/widget.js"
        async defer></script>
On your server go 
form := url.Values{
    "secret":   {os.Getenv("CAPTCHA_SECRET")},
    "response": {r.FormValue("pcaptcha-response")},
}
res, err := http.PostForm(
    "https://captcha.example.com/v1/siteverify", form)

// decode, and reject the request
// unless success is true

React and Vue wrappers ship in the repository, and the verification call is a plain form post — there is nothing to install on your backend.

06 / Deploy

Run the whole thing in one command

The demo stack brings up the service and a page carrying every challenge type, each on its own site key, with the server-side verification wired up behind every form.

Demo stack sh 
git clone https://github.com/avestura/persian-captcha
cd persian-captcha
docker compose -f docker-compose.demo.yml up --build

# the service on :8080
# every challenge on :5173
Site keys yaml 
sites:
  - name: "Your site"
    key: "pc_site_..."
    secret: "pc_secret_..."
    allowed_origins: ["https://example.com"]
    locale: "fa"
    difficulty: "normal"
    challenge_rate: 0.25

The configuration file is re-read when it changes, so keys and origins rotate without a restart. Everything in it can come from the environment instead, which means a container deployment needs no file at all.

Clone it, run it, read all of it

Go with no external dependencies — not for HTTP, not for YAML, not for Redis, not for image rendering. A dependency tree you can read in an afternoon is worth more than the code it saves.
